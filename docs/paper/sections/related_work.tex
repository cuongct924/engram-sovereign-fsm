\section{Related Work}
\label{sec:related}

\subsection{BFT Consensus and Atomic Distributed Objects}
Tendermint~\cite{buchman2016tendermint} and its CometBFT successor provide
partially synchronous BFT consensus with deterministic finality, and form
the base layer our protocol extends. Their safety and liveness proofs, like
most BFT consensus literature, are stated over a closed validator set whose
own network is the only communication channel considered; the liveness of
any \emph{external} dependency, such as a settlement or DA layer, is outside
the model. More recent work on atomic distributed objects, such as
AdoB~\cite{honore2024adob} and Adore~\cite{honore2022adore}, generalizes BFT
consensus to certified reconfiguration and richer object semantics, but
again within a single, self-contained fault domain. Engram differs by making
the health of \emph{external} layers itself an object the consensus protocol
must reach quorum agreement on, rather than an assumption external to the
model.

\subsection{Leader-Based vs.\ DAG-Based BFT Consensus}
HotStuff established the modern template for leader-based BFT consensus,
achieving linear communication complexity and responsiveness in the
partially synchronous model~\cite{yin2019hotstuff}; CometBFT, which Engram
extends, is part of this same leader-based lineage. A separate line of work
instead decouples transaction dissemination from ordering using a
directed-acyclic-graph (DAG) mempool: Narwhal separates reliable
dissemination from consensus so that throughput is no longer bottlenecked by
the ordering protocol~\cite{danezis2022narwhal}, and Bullshark builds a
zero-message-overhead ordering rule on top of a Narwhal-style DAG to reach
practical, low-latency partial-synchrony
performance~\cite{spiegelman2022bullshark}. These DAG-based designs target a
different bottleneck than Engram does: they optimize raw consensus
throughput under a closed, always-available validator set, whereas Engram's
problem is what the validator set should do when \emph{external, peripheral}
infrastructure (Bitcoin, DA) becomes unavailable. Engram therefore builds on
the simpler leader-based CometBFT core -- compatible with the existing
Cosmos SDK ecosystem it targets -- rather than a DAG mempool; adapting the
FSM sensor-and-fallback design to a DAG-based core such as Narwhal/Bullshark
is an orthogonal engineering direction we do not explore here.

\subsection{Modular Blockchains and Data Availability}
LazyLedger, the design that became Celestia, decouples data availability
from execution and introduces client-side data-availability
sampling~\cite{albassam2019lazyledger} so that light clients can verify data
is published without downloading it in full. This line of work specifies how
to make a DA layer efficiently \emph{verifiable}, but treats DA-layer
liveness itself as an assumption: if the DA network stalls, execution layers
built on top of it have no specified fallback. Beyond Celestia's original
sampling design, more recent work targets the peer-to-peer networking layer
of DAS itself: Coded Distributed Arrays apply network coding to the
sampling network to jointly improve storage efficiency, communication
overhead, and Byzantine robustness relative to Ethereum's current DAS
networking layer~\cite{phamminh2026cda}. Engram's DA gap sensor
(Section~\ref{subsec:sensors}) is agnostic to which sampling-network design
backs it -- it adds an explicit consensus-level response (degrading to a
local fallback) for the case that the DA layer's liveness assumption does
not hold, regardless of which DAS construction is underneath; and
Section~\ref{subsec:sim-to-real} discusses why the current prototype does
not yet implement full DAS against many independent peers.

\subsection{Bitcoin-Anchored Settlement}
\label{subsec:settlement}
Babylon repurposes Bitcoin's proof-of-work as a settlement and slashing
layer for proof-of-stake chains via timestamped
checkpoints~\cite{tas2022babylon}. This class of design provides a strong
settlement anchor but, again, assumes that anchor remains reachable and
un-reorged. Engram's Bitcoin finality gap sensor
(Section~\ref{subsec:sensors}) and its threat-model boundary on reorg depth
(Section~\ref{subsec:formal-invariants}) make the anchor-availability
assumption explicit and formally bounded, rather than implicit. We note
that Engram's accountability mechanism
(Section~\ref{subsec:formal-invariants}) is deliberately different from
Babylon's: it detects equivocation via CometBFT's own evidence pool at the
Engram consensus layer, rather than extracting a validator's private key
through a Bitcoin-published extractable one-time signature. The two are
different security models solving different problems -- Babylon lets
Bitcoin itself slash stake, whereas Engram uses Bitcoin only as a settlement
and finality anchor -- and we do not claim Babylon-style,
Bitcoin-enforced slashing as part of this system.

\subsection{Eclipse and P2P-Layer Attacks}
Rehman et al.\ survey eclipse attacks in blockchain
P2P networks, showing that node-discovery poisoning, peer-eviction gaming,
and network-level routing control can combine to stay hidden from any single
metric such as raw peer count~\cite{rehman2025eclipse}. This motivates
Engram's tri-interface P2P health profiler
(Section~\ref{subsec:sensors}), which combines six structural, behavioral,
and temporal bounds rather than relying on peer count alone -- while, as we
discuss in Section~\ref{sec:discussion}, still sharing the scope limitation
that survey identifies: static aggregate bounds do not substitute for
cryptographic peer authentication.

\subsection{Formal Verification of Consensus Protocols}
TLA+~\cite{lamport2002specifying} is a well-established specification
language for concurrent and distributed protocols, including prior
Tendermint/CometBFT specification efforts. Engram's verification
methodology builds on the LiDO framework's technique of reducing liveness
properties to a safety obligation on a linking
invariant~\cite{qiu2024lido}, applying it to a four-layer refinement
hierarchy (Section~\ref{sec:formal}) that, unlike prior consensus-only
specifications, also covers the FSM and its interaction with the extended
consensus proposal. A recent systematization of formal verification for
consensus protocols surveys over 20 verified protocols and taxonomizes
verification approaches along a maturity scale from informal reasoning to
machine-checked code proofs~\cite{bondarev2026sok}; in that taxonomy,
Engram's approach sits firmly in the \emph{explicit-state model checking}
family (TLC, and Apalache for bounded SMT-based checks), which is
well-suited to catching concrete counterexamples on a finite-scope model
but, unlike \emph{deductive verification} tools such as Coq/Rocq or Agda,
cannot itself prove a property for arbitrary $N$ and $f$ -- consistent with
the small-scope threat noted in Section~\ref{subsec:limitations}. On the
liveness side, an alternative to this paper's refinement-mapping reduction
is to construct an explicit \emph{ranking function} that decreases
monotonically toward progress; recent work on \emph{implicit rankings}
shows how to carry out such ranking-function liveness proofs automatically
in first-order logic, which could offer a deductive complement to Engram's
model-checked liveness result in future work~\cite{lotan2025implicit}.

\subsection{Rollup Escape Hatches and Forced Inclusion}
A closely related line of work addresses essentially the same liveness
problem -- what happens when a system's own operator or dependency layer
stops cooperating -- at a different layer of the modular stack: the L2
rollup sequencer, rather than an app-chain's Bitcoin/DA/P2P dependencies.
When a rollup's sequencer stops producing blocks or censors a user, escape
hatches let users bypass it and withdraw directly against the L1,
typically via a time-based trigger and a Merkle or validity proof against
the last known L2 state
root~\cite{figueira2025escapehatch}. Capretto et al.\ generalize the
sequencer/data-availability-committee pair into a formally specified
``arranger'' object and give a fraud-proof mechanism that guarantees
legal, available, non-conflicting batches even if every arranger replica
is Byzantine~\cite{capretto2025secure}. Both lines of work confirm that
peripheral-dependency liveness failure is a real, actively studied problem
across the modular stack, not one unique to Engram's setting -- but both
solve it with an \emph{L1-anchored, asynchronous fallback path} external
to the L2's own block-production consensus: a user- or watcher-triggered
contract call on a separate chain, exercised only when the primary path is
already stuck. Engram's design differs by keeping the fallback
\emph{inside} the validator set's own BFT quorum: peripheral health is a
field the same consensus vote already agreeing on transactions must also
agree on, with the FSM state committed in the same block rather than
resolved via a separate L1 contract after the fact. This is a narrower,
more specific claim than ``no prior system handles peripheral-dependency
liveness at all''; we state it precisely to avoid overclaiming novelty
against this literature.

\subsection{Scope: Storage and Slashing Layers}
The adaptive-consensus and circuit-breaker concept formalized in this paper
originated as a brief design sketch (four bullet points, no formal model, no
evaluation) in an internal organizational
whitepaper~\cite{engram2026whitepaper}, which describes a substantially
broader system: a token-incentivized, DePIN-operated physical storage
network combining Reed-Solomon erasure coding, zero-knowledge
proof-of-spacetime (zk-PoSt, built on Groth16~\cite{groth2016size} and
Poseidon), and Bitcoin-anchored slashing via extractable one-time
signatures. That storage network -- including its token economics, its
Groth16-based zk-PoSt circuit, and its EOTS-based slashing -- is being
developed by other members of the authors' organization and is
\textbf{out of scope} for this paper: none of it is implemented, formally
verified, or evaluated as part of the artifact described here. Two details
are worth noting for readers cross-referencing that document: first, the
whitepaper's sketch ties its fallback fork-choice rule to
stake-weighted voting power of a native token, whereas this paper's
formalized design generalizes that to a standard $n=3f+1$ Byzantine
quorum with no token dependency; second, the whitepaper's zk-PoSt circuit
(Groth16, for storage-proof privacy) is unrelated to this paper's
re-anchoring proof circuit (Noir/UltraHonk, for FSM-transition and
withdrawal-lock legality, Section~\ref{subsec:reanchoring}) -- the two
systems use different zero-knowledge constructions for different purposes.
This paper's contribution relative to that sketch is the four-state
formalization (adding \textsc{Suspicious} and \textsc{Recovering} with
hysteresis), the TLA+ safety/liveness proofs and ablation study
(Section~\ref{sec:formal}), and the live empirical evaluation
(Section~\ref{sec:evaluation}) -- none of which existed in the original
sketch.

\smallskip
\noindent\textbf{Positioning.} Unlike the systems above, Engram treats
peripheral-layer health (Bitcoin settlement, DA, and P2P) as a first-class,
quorum-agreed consensus variable, backs the fallback state machine with
machine-checked, per-layer safety and liveness properties, and validates
that design against a live multi-layer testbed rather than a single-layer
simulation or a purely theoretical model.
